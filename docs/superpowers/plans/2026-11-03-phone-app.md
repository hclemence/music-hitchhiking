# Music Hitchhiking — Plan 3: Phone App (on sample songs)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the phone-first web app (Start, Explore with 3D map, mini-map, History, Inbox, Ship, Dock) on top of Plan 1's backend, running on a curated sample catalogue until Plan 2 imports real songs, plus a self-contained demo build that can be opened on a phone without any server.

**Architecture:** A Vite + React + React Three Fiber app in `app/` talks to a `Backend` interface. `SupabaseBackend` calls Plan 1's views and RPCs; `DemoBackend` runs the same rules in the browser on the sample map and stores state in `localStorage`. Pure logic (journey tree, mini-map layout, star buffers) is separated from components and unit-tested; screens are tested with React Testing Library against `DemoBackend` or a test double; one Playwright run covers the full live flow at phone size.

**Tech Stack:** React 19, Vite, TypeScript (strict), `three` + `@react-three/fiber` + `@react-three/drei`, `@supabase/supabase-js` v2, Vitest + React Testing Library + jsdom, Playwright (preinstalled Chromium), `vite-plugin-singlefile` for the demo build.

**Spec:** `docs/superpowers/specs/2026-11-02-music-hitchhiking-design.md` (sections 2, 3, 9, 10, 11 drive this plan). Backend contract: Plan 1 migrations `20261102000100`–`0700`.

## Global Constraints

- Phone first: portrait layout at 390×844 must work with no horizontal scroll; touch controls (drag orbit, pinch zoom, double-tap focus). Desktop works but is not optimised.
- No text labels on the map. Area colours come from `regionPalette(colourSeed, …)`, unique per viewer. One ship model for everyone, tinted by `ship_colour`.
- Sample ships render translucent and their card says "Sample".
- Encounters only via core `findEncounters`; exclusions: own dock (from `my_dock`), today's path songs, docks already shown at this hop.
- Hitchhike flight ≈ 1.5 s with the camera following. Home, Find and inbox Visit are `jump` hops, drawn dashed on the mini-map. Tapping a mini-map node calls `move_to` (no new hop).
- Reload stars and docks on app open, on returning to foreground, and every 5 minutes.
- Device pixel ratio capped at 2. Target 60 fps on a mid-range phone; no WebGL2 → a static "needs a newer browser" message.
- Recovery code: generated on the phone and stored before calling `redeem-invite`; shown once with the warning that the account cannot be recovered without it.
- Never display or store another person's user id. The client only ever sees dock ids, trace ids and ship colours.
- Streaming buttons open `spotify_url`, `apple_url`, `youtube_url` in a new tab/app.

**Plan decisions beyond the spec:**
- **Sample catalogue:** about 360 real, well-known songs in 12 hand-picked clusters (no genre names stored or shown), laid out by a deterministic script — not by similarity data, which arrives in Plan 2. Song ids and `mbid`s are deterministic UUIDs derived from artist + title; links are streaming-service search URLs. Plan 2 replaces all of it.
- **Song search for docking** searches stored songs only, via a new member RPC `search_songs`; Plan 2 adds MusicBrainz search for songs not yet on the map.
- **Demo build:** a single-file HTML build using `DemoBackend` (no accounts, no traces/inbox, since there are no other real people) so the map can be tried on a phone by publishing it as an Artifact.

## Review Focus

1. A hop or like fails because the network dropped → the UI applies it immediately, shows an "offline" banner, retries with backoff, and the journey tree does not end up duplicated or forked. (Task 4)
2. The phone is still open past 4am → the next hop returns `bad_hop`; the client starts today's journey at the current song and repeats the hop, without an error screen. (Task 7)
3. The current song is not in `active_stars` (home faded, or reached by Home/Find/Visit) → the client places it via `get_songs` and still shows encounters. (Task 7)
4. No candidates even after widening → the encounter area says "Nobody nearby — try Home or wait" instead of staying blank. (Task 7)
5. Recovery code entered with lowercase letters, spaces or missing hyphens → accepted (core `decodeRecoveryCode`); a wrong code shows "That code didn't work" without signing anyone out. (Task 8)
